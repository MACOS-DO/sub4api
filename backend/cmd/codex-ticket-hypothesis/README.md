# Codex ticket hypothesis watch

This direct-upstream experiment uses the normal OAuth Responses request builder and `HTTPUpstream.Do`, pinned to Codex `0.156.1`. It does not exercise gateway ticket caching or WebSocket routing. Node 20+ runs the bundled ModelTrace browser challenge generator, scorer and fingerprint bank (commit `55a2e4a55170423b484d701e9a82ab62b268c811`) locally.

Copy `.env.example` to `.env`, fill `ACCESS_TOKEN`, `CHATGPT_ACCOUNT_ID`, `MODEL`, and optionally `PROXY_URL`. Keep `.env` private. From `backend/`, run:

```sh
go run ./cmd/codex-ticket-hypothesis -env cmd/codex-ticket-hypothesis/.env -watch-duration 1h
```

To replay the visible initial context from a Codex Desktop JSONL recording, add `-session-jsonl '/mnt/c/Users/mckkm/.codex/sessions/2026/09/23/rollout-2026-09-23T01-51-31-01a0cd76-85e6-7290-92dc-8b5d4f79361e.jsonl'` to the same command. The source file is read-only. Replay preserves the fixed base and app instructions, replaces the mutable memory/skills/permissions/collaboration/delegation templates with one sentence each, switches the visible timezone to `Asia/Singapore`, and replaces the recorded integer task with the fresh ModelTrace challenge. Assistant answers and reasoning are excluded. A missing or unexpected recording fails before contacting upstream. Without this flag, requests keep their original one-user-message shape.

Replay uses one new UUIDv7 for both session and thread during a run, and a new UUIDv7 turn ID for every upstream request. It reads the Codex installation UUIDv4 from the recording's `.codex/installation_id` when available; otherwise it creates a private `.codex-installation.env` next to the dedicated `.env`. Session, thread, turn and window values are checked for consistency between request metadata and outgoing headers. The HTTP identity remains the pinned `codex-tui/0.156.1` rather than the recorded Desktop binary, so replay is an approximation of the visible context, not a guarantee of identical Desktop behavior or improved ticket yield.

For an authenticated proxy, use `PROXY_URL=socks5h://username:password@IP:PORT` or `PROXY_URL=http://username:password@IP:PORT`. Percent-encode URL-reserved characters in usernames and passwords. Each invocation creates a new timestamped log under `logs/` beside the chosen `.env`; the startup line prints its absolute path. The directory is private (`0700`) and each file is created exclusively with `0600` permissions. The same unbuffered output goes to the terminal and file, including startup checks, worker blocks, heartbeats, summary and exit errors. If a log cannot be created or written, the experiment stops rather than silently continuing. Logs are never overwritten or automatically deleted.

If a SOCKS URL reports `unexpected protocol version 72`, check whether the configured port actually speaks SOCKS5; an HTTP proxy requires an `http://` URL. This proxy-protocol error stops the experiment instead of retrying and prints only the configured scheme, host and port, never proxy credentials. A proxy-side CONNECT `403` or `407` also stops without retrying; this does not change the retry policy for upstream HTTP 4xx/5xx. Changing the scheme alone cannot resolve a proxy-side `403` such as `forbidden ip=... not supported`: check the provider's source-IP authorization and account/endpoint eligibility before retrying.

The one-hour limit starts at launch. Three independent workers each send one locally generated challenge at a time. After a complete attempt and its single-output ModelTrace scoring, that worker waits exactly 100ms before its next request; starts from different workers need not be spaced apart. Search freezes the first completed, successfully scored response that matches the requested model and carries both a nonempty turn-state and an applicable cookie. Any search requests already in flight finish before validation begins; they never replace the chosen ticket. The three validation workers then concurrently reuse this same frozen ticket and cookie. Each request has a five-minute timeout within the overall one-hour deadline.

HTTP 4xx (including 401, 403 and 429), HTTP 5xx, transport failures and incomplete streams are logged and retried after the same per-worker 100ms wait. This intentionally ignores `Retry-After` even for 429, which can aggravate rate limiting or account protection; this is an experiment, not a recommended production retry policy. Local preflight/configuration failures still terminate the run. Only complete and successfully scored validation responses contribute to the matching-rate denominator.

The terminal labels every request and 15-second heartbeat by stage, worker and request number. Each completed request's full unmasked request/response turn-state and Cookie/Set-Cookie values, attribution and comparison are printed as one block so concurrent results do not interleave. Request Cookie and response Set-Cookie are different HTTP fields; comparisons use only same-name cookie values and report “无法比较” if no pair exists. A single-output closed-set probability is not independent proof of upstream model identity; concurrency may also affect the result, so do not directly compare this rate with serial runs.

**Both terminal and log files contain reusable session state and cookies without redaction.** Keep the private log directory secure and do not share either output. The program does not print OAuth tokens or proxy passwords and does not pass those credentials to the local Node scorer.
